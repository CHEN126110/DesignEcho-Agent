# 设计 Agent 系统 · 架构优化方案

> 基于思维导图《设计Agent》整理，整合三部分内容：架构评审与优化、工具与能力边界、自我改进机制。
> 本文是对原导图的**增量优化层**——A0–A9 各 Agent 的详细流程定义仍以原导图为准，此处不重复。
>
> 版本：V1.0 · 2026-07-02

---

## 0. 总览

### 0.1 对原架构的评价（保留项）

原方案骨架扎实，以下设计正确、直接保留：

- 共享状态 Design Project State，避免各 Agent 各自理解项目导致信息断层
- 每个 Agent 都有输入 / 输出 / 质量检查的"契约式"定义
- 按问题类型退回对应节点，而不是笼统重做
- 10 个逻辑 Agent 与 6 个部署模块分离（逻辑 Agent = 提示词 + 字段读写权限，不必是独立服务）
- A1 Brief 区分确认项 / 假设项 / 缺失项

### 0.2 三条优化原则

1. **成败在两处**：上游 A1–A6 全是文字进、文字出，LLM 天然擅长，基本一定跑得通；系统成败在"文字变像素"的 A7 和"判断好坏"的 A8。
2. **能用代码确定性解决的，不交给模型碰运气**：尺寸、禁词、版权、导出、归档都是代码的事。
3. **自我改进的上限 = 评价信号的可靠度**：系统只能改进到"自己能分辨好坏"的程度为止。

### 0.3 四层能力模型

| 层 | 决定什么 |
|---|---|
| 架构 | 系统能不能长大（流程闭环、可迭代） |
| 工具 | 手够不够用（抠图、生图、渲染、导出） |
| 资产 + 提示词 | 第一版做出来的东西能不能看 |
| 评测闭环 | 第二个月是否比第一个月好 |

四层都要，缺哪层哪层就是短板。**架构 + 工具只保证下限，上限由资产、提示词和评测决定。**

## 1. 逻辑架构

### 1.1 Agent 一览（含执行主体重新定位）

| 编号 | 名称 | 职责一句话 | 执行主体 | 关键产出 |
|---|---|---|---|---|
| A0 | 接单与分流 | 判断任务类型、信息缺口、分流派工 | 小模型 | 工作流计划、缺失清单 |
| A1 | 需求 Brief | 把模糊需求转成结构化 Brief | 小模型 | Brief（确认/假设/缺失三态） |
| A2 | 素材理解 | 产品识别与素材诊断 | 视觉模型 | 产品卡、素材诊断、缺口清单 |
| A3 | 用户洞察 | 痛点、购买疑虑、竞品表达 | 强模型 | 痛点矩阵、设计机会点 |
| A4 | 卖点文案 | 卖点层级 + 可上图文案 | 强模型 | 文案矩阵、风险词清单 |
| A5 | 视觉方向 | 参考拆解 → 3 个可执行方向 | 视觉模型 | 方向建议、Moodboard 结构 |
| A6 | 版式规划 | 策略 → **版式 JSON** | 强模型 | 版式 JSON、执行清单 |
| A7 | 渲染引擎 | 版式 JSON → 设计稿 | **代码（非模型）** | 初稿、多版本、源文件 |
| A8 | 审核 | 硬规则 Lint + 软判断 | **代码 + 视觉模型** | 审核报告、结构化修改指令 |
| A9 | 交付复盘 | 导出、归档、经验沉淀 | 代码为主 | 交付包、知识库更新 |

### 1.2 与原方案的差异

- A7 从"执行生产 Agent"重新定位为**渲染引擎**——它是要自建的产品，不是接一个现成工具（约占第一版一半工程量）
- A8 拆成硬规则与软判断两层（见 4.3）
- 新增三个人工确认点（见第 5 节）
- 新增 A0 分流三通道（见 3.1）
- 新增字段级状态与依赖图的 State 升级（见第 2 节）

## 2. 共享状态升级：Design Project State

### 2.1 字段通用属性（不再是裸值）

把 A1 Brief 里"确认项/假设项/缺失项"的机制升级为整个 State 的通用字段属性：

```json
"selling_points": {
  "value": ["过膝不下滑", "亲肤不勒腿", "显腿长"],
  "status": "confirmed",
  "written_by": "A4",
  "updated_at": "2026-07-02T10:30:00",
  "confidence": 0.85,
  "source": "产品事实 + 用户评论"
}
```

- `status`：`missing` / `assumed` / `confirmed` 三态。凡是推测（如拿不到真实评论时的行业经验），必须标 `assumed`，不许让系统把猜测当事实用。

### 2.2 字段依赖图与脏标记

```
copywriting ← selling_points ← product_facts + user_pains
layout_plan ← copywriting + visual_direction + material_assets
```

- 上游字段变更 → 下游字段自动标 `dirty` → A0 据此决定重跑哪些环节
- **退回机制的正确性靠依赖图保证，不靠约定**

### 2.3 单一写入者

每个字段只允许一个 Agent 写入（如 `product_facts` 归 A2、`user_pains` 归 A3），A2 ‖ A3 并行时才不会互相覆盖。A0 只做合并与调度，不改业务字段。

## 3. 运行流程

### 3.1 A0 分流三通道（别让每单都走全流程）

| 通道 | 触发条件 | 路径 |
|---|---|---|
| 全新设计 | 新品 / 无历史项目 | 全流程（3.2） |
| 迭代修改 | 已有终稿，改文案 / 换素材 / 改尺寸 | 直接跳 A4 / A6 / A7 |
| 批量套版 | 指定模板 + 替换内容 | 只走 A7 |

第一个项目之后，真实请求大多是后两种——这是成本和速度上最大的一笔优化。

### 3.2 标准流程（全新设计）

1. 用户输入需求与素材 → A0 分流、列缺口
2. A1 生成 Brief → **【人工确认① 核对假设】**
3. A2 ‖ A3 **并行**（A3 对 A2 产品卡的依赖改为可选），汇合进 A4
4. A4 提炼卖点与文案
5. A5 给出 3 个方向（配 A6 粗略缩略图）→ **【人工确认② 选定方向】**
6. A6 输出版式 JSON
7. A7 渲染 → Lint 硬规则 → A8 软审
8. 不通过：A8 输出结构化修改指令 → A7 在 JSON 上**定点修改**（≤3 轮，超限升级人工）
9. 通过 → **【人工确认③ 终稿放行】**
10. A9 导出交付 + 复盘沉淀 → 知识库反哺 A5 / A6

### 3.3 回退规则升级（原"按问题类型退回"保留，追加三条）

- **轮次上限**：A7↔A8 ≤ 3 轮；跨阶段回退整个项目设总预算，超限升级人工，杜绝无限循环与震荡（这轮嫌标题大、下轮嫌不突出）
- **退回 ≠ 重做**：修改指令指向图层 ID，A7 做定点修改，保住已经通过的部分
- 回退动作触发依赖图脏标记，只重跑受影响的字段与环节

## 4. 关键工程决策

### 4.1 版式 JSON（A6 → A7 的中间表示）★ 全系统最重要的一个决定

**为什么**：它让"定点修改、程序化检查、多尺寸延展、人工改稿 diff 采集"全部成为可能——第 3、4、7 节的机制都建立在它之上。

Schema 示例：

```json
{
  "canvas": {
    "width": 1080, "height": 1080, "dpi": 72,
    "format": "jpg",
    "safe_area": { "top": 60, "bottom": 60, "left": 40, "right": 40 }
  },
  "meta": {
    "project_id": "P-2026-0702-01",
    "version": "V02",
    "direction": "强转化直接表达",
    "template_id": "T-017"
  },
  "layers": [
    {
      "id": "bg_01", "type": "background", "z": 0,
      "source": { "kind": "ai_generated", "prompt": "浅灰渐变影棚氛围", "asset_ref": null },
      "rect": { "x": 0, "y": 0, "w": 1080, "h": 1080 }
    },
    {
      "id": "product_main", "type": "image", "z": 10,
      "source": { "kind": "asset", "asset_ref": "img_03_cutout" },
      "rect": { "x": 420, "y": 180, "w": 620, "h": 820 },
      "effects": { "shadow": "soft" }
    },
    {
      "id": "title_main", "type": "text", "z": 20,
      "content": "过膝不下滑",
      "style": {
        "font": "授权字体A", "size": 96, "weight": 700,
        "color": "#1A1A1A", "align": "left", "line_height": 1.15
      },
      "rect": { "x": 72, "y": 200, "w": 400, "h": 220 }
    },
    {
      "id": "tag_01", "type": "component", "z": 21,
      "component": "selling_point_tag",
      "props": { "text": "亲肤不勒腿", "icon": "check" },
      "rect": { "x": 72, "y": 460, "w": 260, "h": 64 }
    },
    {
      "id": "logo", "type": "image", "z": 30,
      "source": { "kind": "asset", "asset_ref": "brand_logo" },
      "rect": { "x": 72, "y": 940, "w": 180, "h": 60 }
    }
  ]
}
```

扩展约定：

- **详情页**（多屏长图）：顶层加 `sections[]` 分屏结构，每屏内部与上面同构，复用同一套流程
- **多尺寸延展**：同一份 JSON + 尺寸适配规则，自动生成主图 / 横版 banner / 详情页头图——电商最高频需求

### 4.2 渲染引擎选型

| 路线 | 优点 | 代价 | 建议 |
|---|---|---|---|
| HTML/CSS + 无头浏览器截图 | 文字、字体、对齐完全可控；改版 = 改 JSON | 需自建组件库 | ★ V1 首选 |
| 模板引擎（HTML/PSD 模板填充） | 上手最快、质量下限高 | 灵活度低 | V1 并行 |
| Figma API | 协作好、可交付源文件 | 工程量中 | V2 |
| PS / UXP 脚本 | 保真最高、交付 PSD | 工程量大 | V2+ |
| 整图文生图 | 快 | 文字渲染不可控、产品变形 | ✗ 禁用于成品 |

**混合出图原则**：产品 = 实拍抠图；背景 / 氛围层 = 生图模型；文字 / 标签 / Logo = 排版引擎。这条同时落实原方案的"保持产品真实感"，并规避"与实物不符"的合规风险。

组件库（标题、卖点标签、价格角标、细节放大框、对比模块……）需要设计师参与建设或从优秀案例拆解——**出图好不好看，主要来自资产，不来自模型**。

### 4.3 审核双层（A8）

**第一层：硬规则 Lint（代码，先跑，毫秒级、零幻觉，不过关不进模型审）**

- 尺寸 / 分辨率 / 格式 / 安全区
- 禁词与平台敏感词（查规范库）
- 文字溢出、截断、最小字号
- 必现元素（Logo、CTA、必须出现的信息）
- **字体授权白名单**（国内电商字体侵权是真实的诉讼风险，原导图缺此项）
- 图片素材授权状态
- 色值符合品牌 VI

**第二层：软判断（多模态模型，必须看渲染后的成品图，不能看版式描述）**

- 第一眼能否读懂核心卖点
- 视觉层级与阅读路径
- 排版质量、素材质量、品牌一致性、商业转化要素
- 原导图 A8 的十个检查维度全部保留，归入此层

**输出格式：结构化修改指令**（分级 + 指向图层 + 说明原因）：

```json
{
  "verdict": "revise",
  "round": 2,
  "edits": [
    {
      "layer_id": "title_main", "field": "style.size",
      "from": 96, "to": 112,
      "severity": "must", "reason": "缩略图尺寸下第一眼不可读"
    },
    {
      "layer_id": "tag_03", "op": "delete",
      "severity": "should", "reason": "卖点堆砌，与主卖点无关"
    }
  ]
}
```

### 4.4 规范库（独立数据，不写死在提示词里）

平台规范（尺寸/安全区/格式）、禁词库（广告法 + 平台）、字体白名单与授权状态、品牌 VI 规范——统一做成**带版本、可热更新**的数据，所有 Agent 通过工具查询。否则平台规则一改，要改十个提示词。

## 5. 人工确认点（三个，其余全自动）

| 点位 | 时机 | 形式 | 目的 |
|---|---|---|---|
| 确认① 核对假设 | A1 生成 Brief 后 | 一条消息列出假设项，用户点头即可 | 防止方向性跑偏 |
| 确认② 选定方向 | A5 三方向 + A6 粗略缩略图后、正式生产前 | 三选一 | 方向选错是最贵的浪费，此点最省钱 |
| 确认③ 终稿放行 | A8 通过后 | 放行 / 微调 | 审美最终裁判——**长期保留，不是过渡方案** |

## 6. 工具与资产清单 · 能力边界

### 6.1 分环节清单

| 环节 | 现成可接 | 必须自建 | 前期人工顶 |
|---|---|---|---|
| A2 素材理解 | 抠图 API、超分、视觉模型 | 素材诊断提示词 | 素材质量复核 |
| A3 用户洞察 | 视觉模型读竞品截图 | 行业疑虑经验库 | 粘贴评论 / 竞品资料（平台反爬，实时抓取大概率不可行） |
| A4 卖点文案 | 强模型 | 文案风控词库 | 卖点审校 |
| A5 视觉方向 | 图片检索 | 参考拆解提示词、模板效果库 | 初期方向把关 |
| A6 版式规划 | — | 版式 JSON schema、版式知识 few-shot | 版式复核 |
| A7 渲染 | 生图 API（仅背景）、无头浏览器 | ★ 渲染器 + 组件库（约一半工程量） | 疑难稿人工制作 |
| A8 审核 | OCR、色值分析 | ★ Lint 规则引擎、软审提示词 | 审美终审 |
| A9 交付复盘 | 对象存储 | 命名 / 归档脚本（沿用原方案的文件夹与命名规范）、知识库结构 | 复盘录入 |

**护城河四件套：版式 JSON schema、渲染器、Lint、State 文件。Agent 数量不是护城河，提示词才是能力本体**——原导图里的袜子疑虑清单、审核十维度、文案风控规则，都是最好的提示词原材料。

### 6.2 诚实的能力边界（写进预期管理）

- 软审能稳定抓**结构性**问题（层级乱、卖点不清、文字压图）；"高级感、微妙的色彩不协调"这类审美判断当前模型不稳 → 这就是确认③长期保留的原因
- 生图模型做背景氛围可以，精细控制与一致性有限，别指望它兜底整张图
- 用户评论、竞品页面的实时数据大概率拿不到 → 用行业经验库 + 人工粘贴代替，并在 State 里标 `assumed`
- 知识库冷启动为空，前几十单基本靠人工喂模板

## 7. 自我改进体系

> 核心原则：**自我改进的上限 = 评价信号的可靠度。** 让系统变好的关键，不是给它改自己的权限，而是给它一面足够诚实的镜子。

### 7.1 四个层次

| 层次 | 是什么 | 状态 / 建议 |
|---|---|---|
| L1 任务内自我修正 | A8↔A7 审核循环 | 已有；只纠错、不沉淀，下一单还会犯同样的错 |
| L2 资产自我进化 | 知识库 / 模板 / 规则随运行变好 | ★ 先做：回报最高、风险最低 |
| L3 提示词自动优化 | 优化器提案 + 回归评测 + 人工合并 | 回归集就绪后再上 |
| L4 改自身代码 / 流程 | Agent 提 PR，人 merge | 技术上可行，**永不开自动合并** |

### 7.2 L2 信号采集设计（具体方案）

**（a）人工改稿 diff——全系统最值钱的信号。** 因为设计稿是版式 JSON，人在终稿前的每一次修改都是结构化、机器可读的：

```json
{
  "project_id": "P-2026-0702-01",
  "version_from": "V03_auto",
  "version_to": "V03_final",
  "editor": "human",
  "stage": "确认③",
  "edits": [
    { "layer_id": "title_main", "field": "style.size", "from": 112, "to": 96 },
    { "layer_id": "tag_02", "op": "delete" },
    { "layer_id": "product_main", "field": "rect.y", "from": 180, "to": 140 }
  ],
  "task_type": "淘宝主图",
  "template_id": "T-017",
  "direction": "强转化直接表达"
}
```

**（b）自动归因规则：**

- 同类 edit 在同一 task_type / 模板下出现 ≥ 3 次 → 生成候选规则（进 Lint 硬规则，或进 A6 提示词 few-shot）
- 候选规则进入人工审核队列，合并后带版本上线
- 每条规则记录来源 diff，可追溯、可回滚

**（c）CTR 回流：** 交付图上线后回填点击率 / 转化率 → 写入模板与卖点组合的效果元数据 → A5 / A6 选择时按历史效果加权。这是唯一不需要任何模型当裁判的改进回路，也是最客观的。

**（d）知识库准入门槛（防污染）：**

- 仅"人工放行 + 上线数据 ≥ 类目基线"的案例可入库
- 入库去重：同模板同方向只保留表现最优的
- 每条目带来源与效果快照；每季度人工清理一次
- 冲突检测：新规则与既有规则矛盾时挂起，等人工裁决

### 7.3 L3 提示词自动优化流程

```
优化器（强模型）对单一模块提出提示词变体
  → 金标集自动跑分
  → 人看 diff 决定是否合并
  → git 版本化发布
```

三条规矩：

1. 提示词进 git，像代码一样管版本
2. 一次只改一个模块
3. 目标函数警惕 Goodhart 定律：定成"A8 通过率"，优化器最先学会的一定是讨好 A8 或诱导 A8 放水——这在自动优化里是**必然发生**，不是可能发生

参考：DSPy 一类自动提示词优化框架。

### 7.4 裁判分工矩阵

| 判断类型 | 裁判 | 自动化程度 |
|---|---|---|
| 确定性（尺寸 / 禁词 / 溢出 / 版权） | 代码 | 全自动 |
| 结构性（层级、卖点清晰度） | 多模态模型 | 自动 + 定期人工抽检（防"运动员兼裁判"自我强化偏好） |
| 审美（高级感、微妙不协调） | 人 | 长期保留 |
| 策略有效性（模板 / 卖点组合） | 市场数据 | 自动但慢，用于资产层，不用于单张图 |

> 代码领域自我改进跑得快，是因为验证比生成容易（有测试）；设计审美恰好相反——模型看出"哪里不好看"并不比做出好看的图容易多少，纯靠左脚踩右脚上不了天。

### 7.5 改进回路

```
线上运行 → 信号沉淀（改稿 diff · 审核记录 · CTR）
        → 优化器提案（提示词 / 模板 / 规则）
        → 回归评测（金标集自动跑分）
        → 人工审核合并（像 review PR 一样）
        → 版本化发布（可回滚）
        ↻ 回到线上运行
```

安全阀在"发布之前的人工合并"，不是限制它提案。评测不过 → 退回提案。

## 8. 评测与仪表盘

### 8.1 核心指标

- 一次通过率（A8 首轮通过占比）
- 回退次数按原因分布（文案 / 版式 / 执行 / 素材）
- 各阶段耗时与成本
- 终稿前人工改稿 edit 数（越少说明系统越接近人的标准）
- 上线 CTR / 转化（资产层慢指标）

### 8.2 金标回归集

- 10–50 个代表性任务，覆盖任务类型 × 品类 × 平台
- 每个任务含：输入、期望产出要点、历史最佳得分
- **任何提示词 / 规则 / 模板变更，必须先跑回归再上线**——否则改动是盲改，还会静默伤害旧能力

### 8.3 模型分层（成本控制）

A0 / A1 用小模型；A3 / A4 / A6 用强模型；A2 / A5 / A8 软审用视觉模型；A7 是代码不是模型。

## 9. 落地路线图

**阶段 0 · 写代码之前：人肉跑通一单。** 拿一个真实项目（如过膝袜主图），人工扮演每个 Agent，严格按流程和产出物格式手工走完全程。近乎零成本，却能暴露大部分设计问题——哪个环节输出格式不对、哪里信息断了、版式 JSON 缺什么字段。**跑通了再自动化，顺序千万别反。**

**阶段 1 · V1（6 个部署模块）：**

- 模块划分沿用原方案：M1(A0+A1)、M2(A2+A3)、M3(A4)、M4(A5+A6)、M5(A7)、M6(A8+A9)。注意 M6 内部保留"A8 在循环内、A9 在循环外"的边界
- 工程重心放在护城河四件套：版式 JSON schema、渲染器（HTML/CSS 或模板引擎）、Lint、State
- 知识库人工喂模板；三个人工确认点上线；分流三通道上线

**阶段 2 · 数据飞轮：** 改稿 diff 采集与自动归因、CTR 回流、回归集扩充到 30+、L3 提示词自动优化上线。

**阶段 3 · 拆细与延展：** 按瓶颈拆细 Agent、接 Figma / PS 渲染后端、详情页多屏结构、多尺寸自动延展、L4 以 PR 模式试点（永不自动合并）。

## 附 · 一句话总结

架构决定能不能长大，工具决定手够不够用，资产和提示词决定第一版能不能看，评测闭环决定第二个月比第一个月好多少。让系统自己变好的关键，不是给它改自己的权限，而是给它一面足够诚实的镜子。
